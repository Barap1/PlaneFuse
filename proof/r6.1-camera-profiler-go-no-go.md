# R6.1 camera-space stem fusion go/no-go

Status: GO technically justified; implementation stopped at the Phase 2 claim gate pending human direction.

Commit: `5ff39fa`
Command: `./pf bench camera`
Build: Release, arm64, explicit `MLComputeUnits.all`

The committed Release benchmark captured a fresh 300-frame real NV12 replay and
measured the resize boundary separately:

- resize GPU p50: `0.0217 ms`; p95: `0.1131 ms`;
- synchronized resize wall p50: `0.5096 ms`; p95: `0.6843 ms`;
- direct paired B2/C1 post-resize p50 difference: `0.0743 ms`;
- paired median bootstrap 95% CI: `[0.0392, 0.1280] ms`;
- top-1 agreement: `0.9960`, above the declared `0.995` threshold;
- activation max absolute error: `9.059906e-6`, below the declared `1e-5` threshold;
- C full-RGB intermediate bytes: `0`;
- element-by-element CPU activation population bytes: `0`.

Interpretation: synchronized resize wall time is material relative to the direct
paired B2/C1 difference, so a bounded camera-space compilation experiment is
technically justified. This is not evidence that camera-space fusion will improve
the result: GPU resize duration is small, synchronization/mapping dominates, and
the direct strongest-B/C result remains below the competition target. No fusion
variant was implemented or claimed from this go/no-go artifact.
