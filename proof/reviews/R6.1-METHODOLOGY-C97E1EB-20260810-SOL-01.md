## Findings

### F-001

Severity: high
Category: fairness
Evidence: `proof/r6.1-camera-benchmark-plan.md:55-60` makes identical replay optional (“when feasible”); `BENCHMARK_CONTRACT_V2.md:182` requires both pipelines to consume the same captured frames or a paired replay buffer; `Sources/PlaneFuseLive/main.swift:56-99,281-301` retains only the latest live frame and provides no reproducible replay corpus.

Risk: Separate physical-camera sessions expose B2 and C1 to different frame streams, delivery cadence, and camera conditions. This prevents a defensible comparative throughput or capture-to-result claim and violates the mandatory same-input rule.

Required fix: Make an identical persisted or deterministic replay buffer mandatory for comparative B2-only/C1-only throughput. Record its hash, frame identifiers/order, timestamps, pixel format, and replay cadence in both artifacts. If replay cannot be implemented, prohibit comparative throughput claims and restrict live sessions to non-comparative delivery evidence.

Closure evidence: Release B2-only and C1-only JSON artifacts showing the same replay artifact SHA-256, identical frame identifiers/order and configuration, at least 300 processed frames each, and a targeted verification command demonstrating both runs consumed the identical sequence.

### F-002

Severity: high
Category: correctness
Evidence: `proof/r6.1-camera-benchmark-plan.md:31-39` defines callback-arrival-to-result timing, while lines 45-51 require both candidates to process the same frame serially with alternating order; `Sources/PlaneFuseLive/main.swift:146-158` executes B and then C sequentially; `proof/r6-camera-300-frame.json:42` confirms fixed serial order in the successful R6 proof.

Risk: In a serial paired run, the second candidate’s delivery-to-result latency necessarily includes time spent running the first candidate. Alternating order changes which candidate is contaminated but does not make individual latency samples or their median difference equal to isolated capture-to-result latency. A headline CI derived from those samples could therefore be biased or misinterpreted.

Required fix: Define candidate-local post-resize input-to-result latency as the paired-run comparison metric. Derive comparative frame-delivery-to-result latency only from isolated B2-only/C1-only runs using the mandatory identical replay protocol. If serial paired delivery-to-result values are retained, label them order-contaminated, report first/second-order strata separately, and exclude them from headline differences and confidence intervals.

Closure evidence: Revised methodology naming the eligible metric for every CI; persisted raw records containing candidate order and all timestamps; Release JSON with isolated B2-only/C1-only delivery-to-result distributions over the same replay; and a targeted statistics test proving serial predecessor time is excluded from the paired headline metric.

### F-003

Severity: medium
Category: reproducibility
Evidence: `proof/r6.1-camera-benchmark-plan.md:45-51` specifies five batches and a paired bootstrap CI but does not define the resampling unit, treatment of temporal/batch dependence, bootstrap seed/count, median convention, or percentage denominator; `BENCHMARK_CONTRACT_V2.md:99-105` makes the CI decisive for final interpretation.

Risk: Treating temporally adjacent camera frames as independent observations can produce an artificially narrow confidence interval, while unspecified bootstrap and percentage calculations prevent exact reproduction and may change whether the result is positive or inconclusive.

Required fix: Preregister a deterministic statistical algorithm: batch/block or hierarchical resampling unit, handling of within-batch temporal dependence, bootstrap seed/count, median definition, B-minus-C sign convention, percentage denominator, and policy for aggregating batches without cherry-picking.

Closure evidence: Revised plan containing the complete algorithm; a deterministic statistics test fixture with expected p50, p95, mean, MAD, percentage, and CI outputs; and benchmark JSON recording the algorithm version, seed, resample count, batch IDs, raw paired samples, and resulting interval.

## Conclusion

The R6 proof is appropriately labeled as Debug technical-gate evidence and does not overclaim a final speedup, while the proposed B2/C1 pair otherwise matches precision, tail, build, synchronization, and compute-unit policy. R6.1 methodology cannot yet pass because comparative throughput permits unequal inputs, serial paired capture timing can contaminate the claimed boundary, and the decisive bootstrap procedure is insufficiently specified.
