# R6.1 release-grade camera benchmark plan

Status: preregistered implementation plan; no final result is accepted yet.

## Matched pair

The headline pair is B2 versus C1:

- B2: camera NV12 -> native-plane GPU crop/resize -> materialized planar
  Float32 `[3,224,224]` RGB -> ordinary pretrained RGB stem -> persistent
  buffer-backed Float32 `MLMultiArray` -> unchanged Core ML tail.
- C1: camera NV12 -> native-plane GPU crop/resize -> transformed native-plane
  stem -> persistent buffer-backed Float32 `MLMultiArray` -> the same unchanged
  Core ML tail.

Both paths use the same device, source frame, crop/resize contract, Float32
activation layout, command synchronization policy, build mode, and Core ML
compute-unit policy. The selected policy is explicit `MLComputeUnits.all` for
both B2 and C1; the loaded model configuration must record this value in the
benchmark JSON.

The current B1 Debug run and its post-resize measurements are retained as R6
technical-gate evidence only and are excluded from this headline pair.

## Camera and clock boundaries

The delegate records, for every callback, a monotonic callback-arrival time,
the sample-buffer presentation timestamp, callback sequence, and whether the
frame was dropped by `AVCaptureVideoDataOutputSampleBufferDelegate`.

Per processed frame, record these boundaries using the same monotonic clock:

1. callback/frame-delivery arrival;
2. source texture mapping and GPU crop/resize submission/completion;
3. frontend stem completion;
4. model-input-to-result completion;
5. final result extraction.

Report frame-delivery-to-result separately from post-resize model-input-to-result.
The media presentation timestamp is metadata, not a substitute for a common
monotonic clock.

The paired computational headline metric is candidate-local
`post_resize_input_to_result`: it starts when the resized NV12 output is ready
for the candidate and ends after result extraction. It excludes the other
candidate's work. Any serial paired `frame_delivery_to_result` sample is
explicitly `order_contaminated`, is stratified by first/second execution order,
and is excluded from the paired headline difference and confidence interval.
True live `frame_delivery_to_result` is measured separately in standalone B2-only
and C1-only camera sessions; those sessions are descriptive unless they consume
the identical replay described below.

## Paired latency protocol

The Release camera paired run uses at least 20 warmups followed by exactly 200
paired measured frames per batch and exactly five independent batches. B/C order
alternates per frame and alternates at batch boundaries. The same captured frame
is used by both candidates. Preserve raw per-pair B-minus-C samples, including
frame sequence, batch ID, execution order, and all stage timestamps. The paired
headline difference is `B2_post_resize_input_to_result -
C1_post_resize_input_to_result`; positive means C1 is faster.

Statistics use nearest-rank percentiles (`sorted[ceil(p*n)-1]`), arithmetic
mean, and MAD defined as the nearest-rank median of absolute deviations from
the sample median. The aggregate percentage is `(B2_p50 - C1_p50) / B2_p50 *
100`; it is never computed from a cherry-picked batch. The preregistered paired
bootstrap is hierarchical and deterministic: 10,000 replicates, seed
`0x50464A52`, resample five batch IDs with replacement, then resample contiguous
10-frame blocks within each selected batch with replacement until 200 pairs are
reconstructed. This preserves short-range temporal dependence while treating
independent batches as the outer unit. Report percentile 2.5/97.5% CIs for both
mean and median paired differences. A CI containing zero is inconclusive.
The implementation must reject any batch count other than five and any measured
pair count other than 200. The statistics algorithm identifier is
`r6.1-hierarchical-block-bootstrap-v1`.

## Throughput protocol

Capture a deterministic replay buffer of real camera frames as a mandatory
precondition for comparative standalone throughput. The buffer stores the
resized NV12 Y and UV payloads plus frame IDs, source presentation timestamps,
source callback sequence, pixel format, dimensions, and replay cadence in a
binary payload plus manifest. Persist its SHA-256; both B2-only and C1-only
artifacts must record the same replay hash, frame IDs/order, and configuration.
If capture or replay verification fails, the benchmark must refuse a comparative
throughput result.

Run separate Release B2-only and C1-only sessions over at least 300 processed
replay frames each. Separately run standalone physical-camera B2-only and
C1-only sessions to measure true live frame-delivery-to-result; these live
sessions are not a paired comparative claim unless they consume the identical
replay. Report wall-clock duration, callback rate, processed-frame count,
callback sequence range, dropped-frame callbacks, late-frame callbacks,
skipped/overwritten frames, sustained processed FPS, and frame-delivery-to-result
statistics. These runs must not be substituted by the paired-run serial timing.

## Environment and quality

Persist commit, device class, architecture, OS/Xcode/Swift versions, Release
configuration, model/source hashes, exact input format, compute-unit policy,
thermal state at start/end and per batch when available, AC/Low Power Mode
state when available, resource logical/allocated bytes, CPU activation-copy
bytes, GPU command-buffer/synchronization counts, and all configuration values.
Record the statistics algorithm version, bootstrap seed, replicate count, block
size, batch IDs, paired sign convention, percentile convention, and replay
manifest hash in every result artifact.

Retain the existing quality/parity contract and report it with the same build:
at least the current 32-sample corpus initially, then the R7 target of 64 total
inputs (32 provenance-bearing real images and 32 procedural stress inputs),
top-1/top-5 agreement, activation max/mean error and cosine similarity,
probability-vector max absolute error and L1 distance, and every disagreement.
