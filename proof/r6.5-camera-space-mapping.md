# R6.5 camera-space mapping reference proof

Status: CPU/reference correctness prerequisite only. This document does **not** prove a future Metal candidate, its resource lifetime, parity, or performance.

## Accepted operation order

For an even NV12 luma frame of width `W` and height `H`, the current camera bridge uses:

```text
S  = min(W, H) & ~1
OX = ((W - S) / 2) & ~1
OY = ((H - S) / 2) & ~1
```

The CPU reference deliberately matches `CameraResizeGeometry`: both dimensions must be positive and even, and `S >= 2`. Odd dimensions are rejected rather than masked or rounded, because the live path already rejects them before calculating the bit-masked crop.

The resized luma dimensions are `224 x 224`; resized interleaved UV dimensions are `112 x 112`. For a resized luma sample `(rx, ry)`, the Metal resize shader reads:

```text
Yx = OX + floor(rx * S / 224)
Yy = OY + floor(ry * S / 224)
```

For a resized UV sample `(ux, uy)`, it reads:

```text
Ux = OX / 2 + floor(ux * (S / 2) / 112)
Uy = OY / 2 + floor(uy * (S / 2) / 112)
```

All divisions are integer truncation on non-negative operands. The Swift implementation evaluates the same expression with the overflow-safe identity:

```text
floor(i * S / D) = i * floor(S / D) + floor(i * (S mod D) / D)
```

For the fixed output domains (`i < 224` or `i < 112`), this is algebraically identical while avoiding an intermediate `Int` multiplication overflow.

## Composition with C1

For C1 output `(ox, oy)` and kernel tap `(kx, ky)`, the existing native stem computes:

```text
rx = 2 * ox + kx
ry = 2 * oy + ky
valid = rx < 224 && ry < 224
```

The output domain is `0 <= ox, oy < 112`; the tap domain is `0 <= kx, ky < 3`. Thus no negative coordinate is generated. Invalid bottom/right taps are SAME padding and perform no luma, UV, or per-tap offset read.

For each valid tap, the two-stage scalar reference first obtains the resized coordinate `(rx, ry)`, then reads luma at the `Y` equations above. It obtains UV by applying integer division *before* UV resize:

```text
ux = floor(rx / 2)
uy = floor(ry / 2)
```

Substitution gives the direct camera-space form:

```text
cameraYx = OX + floor((2 * ox + kx) * S / 224)
cameraYy = OY + floor((2 * oy + ky) * S / 224)

cameraUVx = OX / 2 + floor(floor((2 * ox + kx) / 2) * (S / 2) / 112)
cameraUVy = OY / 2 + floor(floor((2 * oy + ky) / 2) * (S / 2) / 112)
```

The direct reference computes these substituted expressions independently; the two-stage reference calls the resize-coordinate functions after calculating `(rx, ry)`. Both return the same mapping record, including the resized coordinates, source coordinates, and invalid SAME taps.

## Checked boundaries

`CameraSpaceMappingTests` exhaustively compares every `112 * 112 * 3 * 3` C1 output/tap mapping between the two CPU/reference forms for `1920x1080`, `4x2`, `2x4`, and `224x224` camera dimensions. It also explicitly checks:

- `1920x1080 -> OX=420, OY=0, S=1080`;
- resized luma and UV coordinates at `(0,0)` and `(223,223)` / `(111,111)`;
- the final valid C1 tap `(111,111), (1,1)`;
- the three bottom/right SAME skips at the final output;
- rejected nonpositive, odd, resized out-of-range, output out-of-range, and tap out-of-range inputs.

Passing these CPU/reference tests establishes algebraic coordinate equivalence for the declared operation order. A later Metal fusion candidate still requires independent shader parity tests against this oracle.
