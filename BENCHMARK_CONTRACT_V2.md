# PlaneFuse Phase 2 benchmark contract

This contract extends `BENCHMARK_CONTRACT.md`. Where it is stricter, this file controls Phase 2 work.

## 1. Primary rule

Every performance claim must identify exactly which representation, memory, and execution boundaries differ.

Do not combine improvements from unequal tail implementations, precisions, input paths, bridge methods, or synchronization methods into one percentage.

## 2. Required pipeline matrix

At final evaluation, record every implemented pipeline explicitly:

| ID | Input path | RGB intermediate | Stem | Tail bridge | Tail runtime |
|---|---|---|---|---|---|
| A | standard Apple image path | framework-defined | original | framework-defined | Core ML |
| B1 | native NV12 | RGBA32Float | conventional RGB | boxed/current or matched bridge | matched tail |
| B2 | native NV12 | strongest compact RGB | conventional RGB | matched to candidate | matched tail |
| C0 | native NV12 | none | current native stem | boxed current bridge | current Core ML tail |
| C1 | native NV12 | none | native stem | persistent buffer-backed multiarray | current Core ML tail |
| C2 | native NV12 | none | native stem | IOSurface/Float16 multiarray | Float16-matched tail |
| C3 | native NV12 | none | native stem | MTLTensor | Metal 4 ML tail |
| C4 | native NV12 | none | polyphase native stem | strongest accepted bridge | matched tail |

Only implemented rows should appear publicly. Keep unsupported rows out rather than filling them with placeholders.

## 3. Fair comparison pairs

The key comparisons are:

- B1 versus C0 — preserves the existing result.
- B1 versus C1 — isolates bridge removal while retaining Float32/Core ML.
- B2 versus C2 — compares compact/shared Float16 paths.
- B2/Metal4 versus C3 — compares materialized RGB and native-plane paths on the same GPU-timeline tail.
- strongest B versus C4 — final headline pair.

For each pair, match:

- source frame and frame order;
- color range/matrix/chroma siting;
- crop/resize policy;
- model weights and tail graph;
- tail precision;
- output task;
- command submission count when possible;
- synchronization points;
- build mode;
- warmup and iteration policy.

## 4. Component timing

Before accepting an architectural change, measure the current path into these components where possible:

1. input preparation and texture binding;
2. native or RGB stem GPU execution;
3. command-buffer wait/synchronization;
4. activation-buffer to Swift-array copy;
5. multiarray allocation;
6. multiarray population/boxing;
7. Core ML or Metal ML tail;
8. output extraction;
9. total input-ready to result.

Use signposts or separate deterministic harness regions. Do not infer a component's cost by subtracting unrelated runs if direct measurement is possible.

## 5. GPU timing and profiling

User-visible elapsed time remains important, but Phase 2 final evidence also requires accelerator evidence:

- Metal GPU timestamps or counter samples for stem passes;
- a Metal/Xcode GPU trace or Instruments capture for at least the strongest B and C paths;
- resource inspection showing the RGB intermediate in B and its absence in C;
- synchronization/timeline evidence for any GPU-resident tail claim.

Profiling runs and normal benchmark runs must be separate because instrumentation can perturb timing.

## 6. Statistical protocol

### Quick

- at least 5 warmups;
- at least 20 measured paired iterations;
- alternating B/C order;
- p50, p95, mean, and MAD;
- used only for experiment triage.

### Confirm

- at least 20 warmups unless evidence supports a different value;
- at least 200 paired measured iterations per batch when runtime permits;
- at least 3 independent batches;
- alternating order within each batch;
- preserve raw paired samples or a compact machine-readable distribution;
- report p50, p95, mean, MAD, and the distribution of paired differences.

### Final

- at least 5 independent batches or an equivalent preregistered time-based protocol;
- report a 95% paired bootstrap confidence interval for the median or mean difference;
- report both absolute milliseconds and percentages;
- include system/power/thermal state;
- no cherry-picking a single best batch as the headline.

If the confidence interval includes no improvement, report the result as inconclusive even if one batch is faster.

## 7. Quality corpus

The current four-image corpus is a smoke test, not sufficient final equivalence evidence.

Phase 2 target:

- at least 64 total inputs;
- at least 32 diverse real images with explicit redistribution/license provenance;
- at least 32 procedural stress inputs generated by the repository, covering luma extremes, chroma extremes, edges, checkerboards, gradients, padding boundaries, and chroma-phase patterns.

The real-image count may be reduced only with an explicit documented reason and hostile-review approval.

Report:

- top-1 agreement;
- top-5 set/ranking agreement;
- maximum and mean activation absolute error;
- activation cosine similarity;
- probability-vector maximum absolute error;
- probability-vector L1 distance;
- labels/examples of every disagreement.

Do not translate corpus agreement into population accuracy without a statistically valid labeled dataset.

## 8. Source-model lineage

Final proof must include:

- exact source model URL and SHA-256;
- exact conversion/preparation tool versions;
- derived artifact hashes;
- original Apple image-input model versus derived FullArray task agreement;
- FullArray versus split StemArray+Tail agreement;
- source-derived stem versus B/C activation comparison.

## 9. Memory terminology

Use these terms precisely:

- **logical payload bytes** — dimensions × channels × element size;
- **Metal allocated bytes** — `allocatedSize` or an equivalent runtime resource value;
- **CPU bytes copied** — measured or structurally counted bytes moved through CPU-owned memory;
- **peak memory** — only from actual profiling;
- **bytes avoided** — clearly labeled theoretical or structural difference.

Never call logical payload bytes “allocated bytes” unless the runtime allocation was measured.

## 10. Zero-copy terminology

A path may be called zero-copy only if the relevant storage is shared across the named boundary and no hidden explicit copy is performed by PlaneFuse.

Prefer more precise phrases:

- “no element-by-element CPU copy in PlaneFuse”;
- “buffer-backed multiarray view”;
- “IOSurface-backed shared activation”;
- “GPU-timeline handoff”;
- “no full RGB intermediate.”

Do not infer that Core ML performs no internal copy unless profiler/runtime evidence supports it.

## 11. Camera benchmark

For continuous camera mode, separately report:

- camera frame delivery to source textures;
- crop/resize latency;
- frontend latency;
- tail latency;
- capture-to-result latency;
- sustained FPS over at least 300 frames;
- dropped frames;
- p50/p95 and thermal state;
- per-frame allocation count if measurable.

Both B and C must consume the same captured frames or a paired replay buffer.

## 12. Acceptance rules

An optimization is accepted only if:

1. quality gates pass;
2. its matched conventional baseline is credible;
3. the paired confidence interval supports the claimed direction for final claims;
4. it does not move unmeasured work outside the timing boundary;
5. complexity is proportional to the gain;
6. raw evidence is committed or intentionally stored with a reproducible generation command;
7. the claims ledger is updated.

## 13. Final competition gate

The final strongest path must meet one of the competition-worthiness targets in `SPEC_V2_ADDENDUM.md`.

If it does not, the project may still be technically valuable, but Codex must stop for a human decision before writing a “winning” Devpost claim.
